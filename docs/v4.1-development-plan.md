> 日期：2026-06-05 | 基线版本：v4.0 | 目标版本：v4.1

## 一、项目现状评估

### 已完成（v4.0）

| 模块 | 状态 | 质量 |
|------|------|------|
| 四层状态机 + LangGraph | ✅ 完成 | 架构优秀，可扩展 |
| 8 个 Agent + 5 种协作模式 | ✅ 完成 | Mock LLM，未验证真实效果 |
| 双层缓存（L1 精确 + L2 语义） | ✅ 完成 | 设计合理，未接入 Redis |
| 双层路由（LLM + 规则） | ✅ 完成 | 带降级，但未用真实 LLM 验证 |
| RAG 知识库（ChromaDB） | ✅ 完成 | 只有 3 条 seed 数据 |
| Function Calling（4 个 ERP 工具） | ✅ 完成 | 全部 Mock |
| JWT 认证 + RBAC | ✅ 完成 | 黑名单内存存储 |
| SQLite + SQLAlchemy ORM | ✅ 完成 | 仅适合单机开发 |
| 告警通知（Webhook/Email） | ✅ 完成 | 已实现但未接入真实通道 |
| Prometheus + Grafana | ✅ 完成 | 基础指标，未定制 Dashboard |
| Docker Compose 部署 | ✅ 完成 | 5 服务编排 |
| 前端聊天界面 + 管理后台 | ✅ 完成 | 无流式输出，体验粗糙 |
| 测试套件（319 个） | ✅ 完成 | 100% Mock，无集成测试 |

### 核心差距

1. **从未用真实 LLM 跑通** — 所有测试都是 MockLLM，真实场景下的 token 限制、响应格式、延迟问题未暴露
2. **知识库空壳** — 3 条示例数据，不构成真实问答能力
3. **ERP 对接断裂** — RealAdapter 写好了但从未连接金蝶 API
4. **全局变量架构** — multi_agent_customer_service.py 用模块级全局变量，测试隔离差
5. **前端无流式输出** — AI 回复等待全部生成后才显示，用户体验差
6. **运维能力不足** — 无数据库迁移、无日志聚合、无性能基线

## 二、v4.1 开发计划（六大方向）

### 方向 A：端到端真实跑通（最高优先级）

> **目标**：让系统从"代码能跑"变成"真的能用"

#### A1. 接入真实 LLM API

- **任务**：在 config.py 中支持真实 LLM 配置，通过 OpenAI 兼容接口对接
- **推荐**：DeepSeek（便宜）或 OpenAI（稳定）
- **改动范围**：
  - `config.py`：新增 `LLM_PROVIDER`、`LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL` 配置
  - `multi_agent_customer_service.py`：初始化时根据配置选择 MockLLM 或真实 LLM
  - `agents/base_agent.py`：确保 `_process_with_llm` 能处理真实 LLM 的响应格式
- **验收标准**：`make dev` 启动后，在聊天界面输入"你们有什么精华液？"，得到基于真实知识库的回复

#### A2. 写入真实化妆品知识库

- **任务**：准备 30-50 条真实化妆品 FAQ、产品信息、技术文档
- **内容来源**：参考真实化妆品品牌（如薇诺娜、珀莱雅）的公开信息
- **改动范围**：

  - `knowledge/router.py`：修复 sync 端点对真实 ERP 的兼容
  - 新增 `scripts/seed_knowledge.py`：知识库初始化脚本
- **验收标准**：能回答"敏感肌用什么面霜？""XX 产品保质期多久？"等真实问题

#### A3. 端到端集成测试

- **任务**：编写不依赖 MockLLM 的集成测试
- **改动范围**：
  - 新增 `tests/test_e2e.py`：需要真实 API Key（环境变量控制跳过）
  - 覆盖场景：简单问答、多轮对话、缓存命中、会话漂移检测、知识库检索
- **验收标准**：`RUN_E2E=1 pytest tests/test_e2e.py` 通过

### 方向 B：核心技术债修复

> **目标**：把"演示级"代码变成"生产级"代码

#### B1. 依赖注入重构

- **任务**：消除 `multi_agent_customer_service.py` 中的模块级全局变量
- **改动范围**：
  - 新建 `core/container.py`：依赖注入容器（简单的 Dict + Factory）
  - `multi_agent_customer_service.py`：`build_graph()` 改为接收容器参数
  - `api/app_factory.py`：启动时构建容器并注入
  - `tests/`：适配新的依赖注入方式
- **验收标准**：所有现有测试通过，`build_graph()` 不再依赖模块级全局变量

#### B2. 内存黑名单 → Redis

- **任务**：JWT 黑名单和限流计数器迁移到 Redis
- **改动范围**：
  - `auth/service.py`：`_token_denylist` 改用 Redis Set
  - `auth/rate_limiter.py`（新建）：基于 Redis 的滑动窗口限流
  - `config.py`：新增 `REDIS_JWT_PREFIX`、`REDIS_RATE_PREFIX` 配置
- **验收标准**：重启服务后，已吊销的 JWT 仍然被拒绝

#### B3. SQLite → PostgreSQL

- **任务**：数据库从 SQLite 迁移到 PostgreSQL
- **改动范围**：
  - `db/database.py`：支持 PostgreSQL 连接
  - `requirements.txt`：新增 `asyncpg`、`psycopg2-binary`
  - `docker-compose.yml`：新增 PostgreSQL 服务
  - `docker-compose.override.yml`：开发环境仍可用 SQLite
- **验收标准**：`make prod` 使用 PostgreSQL，`make dev` 仍用 SQLite

#### B4. Alembic 数据库迁移

- **任务**：引入 Alembic 管理数据库版本
- **改动范围**：
  - `alembic.ini` + `alembic/`：初始化迁移框架
  - 生成初始迁移脚本（基于现有 models）
  - `scripts/deploy.sh`：启动时执行 `alembic upgrade head`
- **验收标准**：新增字段时用 `alembic revision --autogenerate` 生成迁移

#### B5. SessionManager 全异步化

- **任务**：消除 `asyncio.to_thread` 的线程池开销
- **改动范围**：
  - `session_manager.py`：`add_message`、`get_context` 改为 async
  - `agents/base_agent.py`：移除 `asyncio.to_thread` 包装
  - 滑动窗口和漂移检测逻辑适配 async
- **验收标准**：SessionManager 所有方法均为 async，无 `to_thread` 调用

## 四、技术方案概要

### 4.1 依赖注入方案（B1）

```
core/container.py
├── LLMContainer          # LLM 实例管理
├── AgentContainer        # Agent 实例管理
├── ServiceContainer      # 服务实例管理（Auth, Session, Cache, etc.）
└── GraphContainer        # LangGraph 构建

使用方式：
container = ServiceContainer()
graph = build_graph(container)
# 替代当前的模块级全局变量
```

### 4.2 流式输出方案（D1）

```
用户发送消息
    ↓
POST /api/chat/stream (SSE)
    ↓
LangGraph 逐步执行
    ↓
每步完成时通过 SSE 推送状态
    ↓
最终回复通过 SSE 逐字推送
    ↓
前端 EventSource 接收并渲染
```

### 4.3 Redis 集成方案（B2）

```
Redis 用途：
├── JWT 黑名单（SET, TTL = token 过期时间）
├── 限流计数器（Sorted Set, 滑动窗口）
├── 会话缓存（替代内存 SessionManager 部分功能）
└── 分布式锁（替代 asyncio.Lock, 多实例部署时）
```

### 4.4 PostgreSQL 迁移方案（B3）

```
兼容策略：
├── 开发环境：.env.dev → DATABASE_URL=sqlite:///./data/dev.db
├── 生产环境：.env.prod → DATABASE_URL=postgresql://user:pass@pg:5432/csdb
├── SQLAlchemy 统一 ORM 层，业务代码无需修改
└── docker-compose.yml 新增 postgres 服务
```

## 五、风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| LLM API 调用费用 | 高 | DeepSeek 价格低；测试用 Mock；设置 token 上限 |
| 依赖注入重构破坏现有功能 | 中 | 分步重构，每步跑通全量测试 |
| PostgreSQL 迁移数据丢失 | 中 | 先实现 SQLite→PostgreSQL 数据迁移脚本 |
| SSE 与 LangGraph 集成复杂 | 中 | 参考 LangGraph 官方 streaming 文档 |
| 金蝶 API 沙箱不可用 | 低 | 保留 Mock 模式作为降级方案 |
