## 1. 模型选型对比

### 1.1 已验证的模型

项目支持 OpenAI 兼容 API，通过 `LLM_PROVIDER` 和 `OPENAI_BASE_URL` 切换。以下是已验证的模型：

| 模型 | 提供商 | 参数量 | 中文能力 | FC 支持 | 延迟(首token) | 价格(输入/输出) | 适用场景 |
|------|--------|-------|---------|---------|--------------|----------------|---------|
| **Qwen2.5-7B-Instruct** | SiliconFlow | 7B | ⭐⭐⭐⭐ | ✅ | ~0.8s | ¥0.35/¥0.70 per 1M | **默认选择**，性价比最优 |
| Qwen3-8B | SiliconFlow | 8B | ⭐⭐⭐⭐⭐ | ✅ | ~1.0s | ¥0.50/¥1.00 per 1M | 中文增强，推理更强 |
| DeepSeek-V3 | DeepSeek | MoE | ⭐⭐⭐⭐⭐ | ✅ | ~1.2s | ¥1.0/¥2.0 per 1M | 复杂推理，高质量输出 |
| GPT-4o-mini | OpenAI | — | ⭐⭐⭐ | ✅ | ~0.6s | $0.15/$0.60 per 1M | 英文为主场景 |

### 1.2 选型决策矩阵

| 维度 | Qwen2.5-7B (默认) | DeepSeek-V3 | GPT-4o-mini |
|------|-------------------|-------------|-------------|
| **中文客服质量** | 足够好 | 最优 | 一般 |
| **Function Calling** | 稳定 | 稳定 | 最稳定 |
| **成本** | 最低 | 中等 | 较高 |
| **延迟** | 最低 | 中等 | 低 |
| **合规** | 国内部署 | 国内部署 | 需跨境 |

**决策**：默认使用 Qwen2.5-7B-Instruct（成本最低、中文能力足够、国内合规），复杂投诉场景可通过协作模式升级（consultation/parallel/react）调用更多 Agent 补偿小模型不足。

### 1.3 选型理由

> **面试话术**：为什么选 Qwen2.5-7B 而不是更大的模型？
>
> 三个原因：1) 客服场景 70% 是高频重复问题，7B 模型配合 RAG 知识库完全够用；2) 成本敏感——假设每天 1 万次对话，Qwen2.5-7B 的月成本约 ¥700，而 GPT-4o 约 ¥15,000；3) 系统通过多 Agent 协作模式补偿小模型不足——简单问题走 Sequential，复杂问题升级到 Parallel/ReAct，多个 7B Agent 协作的效果接近单个大模型。

## 2. Token 成本分析

### 2.1 单次对话 Token 消耗

基于典型客服对话的 Token 消耗估算：

| 组件 | Token 数 | 说明 |
|------|---------|------|
| System Prompt | ~300-500 | 角色定义 + 安全规则 + 专业领域 |
| RAG 上下文 | ~200-800 | Top-3 检索结果注入 |
| 对话历史 | ~100-600 | 滑动窗口，最近 10 轮 |
| 用户输入 | ~50-200 | 平均 50-100 字 |
| LLM 输出 | ~200-500 | 平均 100-200 字回复 |
| **单次调用总计** | **~850-2,600** | 含上下文注入 |

### 2.2 不同协作模式的 Token 成本

| 协作模式 | LLM 调用次数 | 估算 Token/对话 | 适用比例 |
|---------|-------------|----------------|---------|
| Sequential | 1 次 | ~1,500 | ~60% |
| Parallel | 2-3 次 | ~3,500 | ~15% |
| Consultation | 2 次 | ~2,500 | ~15% |
| Hierarchical | 3-4 次 | ~5,000 | ~5% |
| ReAct | 2-5 次 | ~6,000 | ~5% |

### 2.3 月度成本估算（Qwen2.5-7B）

假设日均 1 万次对话，按协作模式分布：

```
日均对话: 10,000 次
加权平均 Token/对话: 1,500×0.6 + 3,500×0.15 + 2,500×0.15 + 5,000×0.05 + 6,000×0.05
                   = 900 + 525 + 375 + 250 + 300 = 2,350 tokens/对话

日均 Token: 10,000 × 2,350 = 23,500,000 tokens/天
月均 Token: 23.5M × 30 = 705,000,000 tokens/月

Qwen2.5-7B 价格: ¥0.35/1M 输入 + ¥0.70/1M 输出
假设输入:输出 = 3:1
月成本: 705M × 0.75 × ¥0.35/1M + 705M × 0.25 × ¥0.70/1M
     ≈ ¥185 + ¥123 ≈ ¥308/月

实际含 RAG 查询改写 + 质量评估 + 路由分类的额外调用：
估算总成本 ≈ ¥500-800/月
```

### 2.4 Token 优化策略

| 策略 | 实现 | 节省比例 |
|------|------|---------|
| **缓存命中** | L1 MD5 + L2 Jaccard，跳过 LLM 调用 | 60-70% 重复问题直接命中 |
| **滑动窗口** | 对话历史 token 级截断，保留最近 10 轮 | 减少 50% 历史 Token |
| **路由分流** | 简单问题走快速通道，不触发复杂协作 | 60% 问题走 Sequential |
| **熔断降级** | LLM 故障时降级到规则引擎，零 Token 消耗 | 故障时 100% 节省 |
| **Token 预算** | 会话级 Token 上限，防止滥用 | 防异常消耗 |

### 2.5 Token 追踪

**代码**：[token_tracker.py](core/token_tracker.py)

系统实时追踪每次 LLM 调用的 Token 消耗，按两个维度聚合：

- **按 Agent**：每个 Agent 的输入/输出 Token 和调用次数
- **按模型**：不同模型的 Token 消耗对比

暴露接口：`/api/metrics/tokens` 返回实时 Token 统计，可用于：
- 监控异常消耗
- 对比不同 Agent 的 Token 效率
- 评估 Prompt 优化效果（优化前后 Token 变化）

## 3. Embedding 模型选型

### 3.1 三级降级链

**代码**：[knowledge_base.py:61](rag/knowledge_base.py#L61)

```
优先级 1: BAAI/bge-small-zh-v1.5    (专为中文优化，326M 参数)
    ↓ 失败
优先级 2: shibing624/text2vec-base-chinese  (通用中文向量)
    ↓ 失败
优先级 3: all-MiniLM-L6-v2          (ChromaDB 默认，英文)
```

### 3.2 效果对比

| Embedding 模型 | Hit Rate@3 | MRR | 说明 |
|---------------|------------|-----|------|
| all-MiniLM-L6-v2 (英文) | 63.3% | 0.500 | 改进前基线 |
| **bge-small-zh-v1.5 (中文)** | **80.0%** | **0.778** | 当前生产配置 |

**提升**：Hit Rate@3 +16.7pp，MRR +55.6%

### 3.3 Reranker 选型

| Reranker | 模型 | 依赖 | 精度 | 速度 |
|----------|------|------|------|------|
| CrossEncoder | BAAI/bge-reranker-base | sentence-transformers | 高 | 慢 |
| BM25 | 无（纯算法） | 无 | 中 | 快 |
| simple_rerank | 无（jieba + 距离混合） | jieba | 中 | 最快 |

降级策略：CrossEncoder → BM25 → simple_rerank

## 4. 面试话术

### Q: "Token 成本怎么控制？"

> 五层优化：1) 双层缓存，60-70% 的重复问题直接命中，不走 LLM；2) 滑动窗口截断对话历史，token 级精确控制；3) 路由分流，60% 简单问题走 Sequential 单次调用；4) 熔断降级，LLM 故障时零 Token 消耗；5) Token 预算上限防滥用。按 Qwen2.5-7B 定价，日均 1 万次对话的月成本约 ¥500-800。

### Q: "Embedding 模型怎么选的？"

> 初期用 ChromaDB 默认的 all-MiniLM-L6-v2（英文模型），评估发现中文 Hit Rate@3 只有 63%。分析原因是英文 embedding 对中文语义理解有天花板。替换为 BAAI/bge-small-zh-v1.5（专为中文优化）后，Hit Rate@3 提升到 80%，MRR 从 0.500 提升到 0.778。系统设计了三级降级链（bge → text2vec → MiniLM），确保模型不可用时自动降级。
